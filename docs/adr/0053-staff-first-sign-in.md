# ADR 0053: A staff temporary password is replaced in place, on whichever app the person was sent to

## Status

Accepted

## Context

ADR 0051 made every created account start with a temporary password, and ADR 0049
put a gate in front of it: while `must_change_credentials` is set, the only
routes a session can reach are `auth/me`, `auth/refresh`, `auth/logout` and
`auth/complete-onboarding`.

That worked because the only such account was the provisioning one, which lives
in the dashboard. Once an administrator can create officers and collectors, the
gate covers accounts whose app is `apps/field` or `apps/collector` — and neither
app had a screen for it. The person could sign in with the temporary password and
then reach nothing at all, on the one device they own.

There is also a wording problem. `complete-onboarding` replaces the **username**
as well as the password, because the provisioning account is literally `admin`
with the password `password`. A staff account was given a real username by an
administrator, written on a handover card. Forcing a rename makes the card wrong
at the moment it is used.

## Decision

- **Staff rotation is password-only.** `POST /v1/auth/change-password` is
  authenticated, available only while the flag is set (`404` afterwards, exactly
  like `complete-onboarding`), keeps the username, replaces the hash, clears the
  flag in the same statement, ends every session the temporary password
  authorised, and returns a session minted from the new password so nobody signs
  in twice. `complete-onboarding` keeps its rename for the wizard.
- **The route is added to `CREDENTIAL_ROTATION_ROUTES`.** The gate refuses
  everything not on that list, so a rotation route missing from it would be
  blocked by the gate it exists to satisfy. The access matrix classifies it as
  authenticated-without-permission, not as a permission an operator can grant.
- **The two phone apps render the screen before anything else.** The flag travels
  in the login and `/v1/auth/me` responses; `App` checks it before the home
  screen. It is not a warning banner, because the server would refuse every
  action behind it.
- **The three app addresses are deployment settings, not tenant config.** One
  deployment serves every tenant from the same frontends, so
  `VITE_ADMIN_APP_URL`, `VITE_FIELD_APP_URL` and `VITE_COLLECTOR_APP_URL` are set
  on the dashboard project. The dashboard address defaults to the serving origin.
  An unset address is reported as unconfigured, never guessed.
- **The handover card is the only place a password is shown, and only once.** The
  server cannot read it back, so create and reset are the only moments a card can
  exist; dismissing it drops the value. Re-opening the card for a still-flagged
  account shows everything except the password.
- **Temporary passwords are generated by default.** Sixteen characters from a
  32-symbol alphabet without `l`, `o`, `0` or `1`, so a value that has to be read
  down a phone line is unambiguous, and the field does not default to whatever
  the administrator types under time pressure.

## Consequences

- An officer or collector can now complete their own first sign-in, on their own
  app, without an administrator doing it for them or a dashboard account existing
  for them.
- The dashboard's `CredentialForm` and the phone apps' `SetPasswordScreen` are two
  implementations of the same idea; they stay separate because the two apps share
  no UI package, and their rules are enforced on the server in one place.
- Moving the addresses into tenant config is deferred: it is the right answer for
  one deployment serving several states with their own domains, and a rebuild of
  one project is cheaper today.
- A person who loses the handover card needs an administrator to reset the
  password again; there is still no mail sender, and no self-service recovery.
